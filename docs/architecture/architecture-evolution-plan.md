## 处理结论

- **保留问题判断**：新增牌种/行为常要改内核枚举和宿主代码；快照、字节编解码与哈希分散手写。生产装载器已落地，八份测试桥接已全部迁移（2026-10-07；2026-10-11 更正），正式宿主接线仍未完成（主稿 T6③）；独立扩展与可靠恢复仍有缺口。
- **先处理已复现阻断**：[进度主稿](native-progress.md#后续待做按阻塞关系)的 P0 存档解码加固先形成通过证据：未知牌种返回错误、载荷必须读尽。v60 回放、标准牌堆循环和 XiaoJi tag 冲突已修并有检查守护，不再重复立项。
- **再做纵向样本**：用一个真实逻辑扩展验证独立装载、选择、保存恢复与错误回滚，由样本决定改哪些内核接口（推荐样本见 §2）。
- **技术选型待验证**：统一 DSL、自动生成全部快照代码、WASM/QuickJS、ISMCTS/强化学习、旧线拆 crate、传输协议与特定渲染库都不能直接作为既定路线。每项先给出独立需求、最小原型、替代方案及验收数据；未立项的候选不阻塞现有扩展切片工作。

## 0 核心判断

原生线（`crates/engine-native`）的事件栈、类型化暂停恢复和字节存档方向正确，但**内容扩展方式是封闭的**：
部分新技能或扩展牌需要修改内核枚举、结算机器、快照和存档编码；`content-native-loader` 已能把包数据转成原生目录，八份测试桥接已全部迁移（2026-10-07；2026-10-11 更正），正式产品接入未完成（主稿 T6③）。
现有封闭行为表尚不足以支撑独立发布的新规则；README 中“扩展独立安装、启停、更新、卸载”的必做能力仍须完整验收。

开放目录/行为、生产侧装载和可恢复状态是必须解决的能力问题；A–F 各节是可比较的实现候选，不构成必须依次完成的阶段门禁。

## 2 候选工作的采用顺序

1. 以[当前进度](native-progress.md)的失败项建立可信基线；先修可复现缺陷，再谈大规模重构和提速。

4. AI、客户端、联机和构建效率分别按功能/性能证据立项。旧线退役只在原生规则、扩展和产品验收后讨论。

## 3 工作流 A：内核开放化

### A0 注册表不变量检查

- **目标**：手写注册表的遗漏与冲突在测试阶段暴露，而不是在恢复或回放时才出现。
- **做法**：
  1. 快照编码 tag 唯一：对 `MachineSnapshot` 每个变体构造样例，编码后检查首字节互不相同，并做编码→解码往返。
  2. 标准目录构成：`standard_catalog_parts` 产出的牌名 × 数量（× 花色点数）与一份显式声明表一致；声明表的来源和取舍写入[规则基准](native-rules-baseline.md)。
  3. `SkillDefId` 只追加：已发布技能的编号顺序不变（编号进入快照和哈希）。
  4. 其他编码表双射：`archive.rs` 中牌种编码表、`HostBehavior` 标签与键之间一一对应。
- **验收**：在修复前的源码上，检查能报出 S13 的两个缺陷（先失败）；修复后通过；新增变体而漏登记时测试失败。
- **落地状态（2026-09-24）**：第 2 点目录构成检查已随主稿 P0「回放与目录」采纳——`tests/standard_catalog_inventory.rs` 声明表检查随 `cargo test` 运行，来源与取舍登记在[规则基准](native-rules-baseline.md#标准目录构成声明表)；修复拆牌循环缺陷后通过（S13 的目录缺陷最初由静态核查发现；2026-09-24 审查在缺陷源码上补跑，该检查 2/2 报红：88≠80、顺手牵羊 8≠4，验收口径的「先失败」由此达成，见[审查修复证据](../operations/evidence/2026-09-24-review-fixes/README.md)）。第 1、4 点已随主稿 P0「N11 字节恢复」采纳——`tests/a0_tag_registry.rs` 对 `MachineSnapshot` 42 变体做 tag 唯一性与编码→解码往返（match 穷尽守卫，新增变体漏登记即编译失败），并在未修复源码上先报出 XiaoJi 往返 UnexpectedEof（S13 的 tag 冲突缺陷，验收口径「先失败」达成）；`HostBehavior` 74 tag 唯一性同测试守护，`CardKind` 86↔0..=85 双射经静态核查确认（编解码函数私有，未行为级测试化）。审查修复（2026-09-24）补第 4 点的数据键部分：`CardKind`、`HostBehavior` 的扩展包数据键双射、键唯一与牌种伴随技能表一致性进入同一测试文件（[ADR 0778](../adr/0778-native-c0-pack-data-keys.md)）；存档牌种编码表仍私有；解码遇未知编号已于 2026-10-07 改为拒绝（加固回归在案，2026-10-11 更正）。第 3 点已随 P1 统一装载落地（2026-10-07）：`standard_skill_ids_append_only` 锁定 standard 目录 46 技能名序（v60 实序），中间插入/重排/删除即失败，只允许尾部追加。2026-10-07 挂靠：第 3 点随主稿 P1 统一装载实施（迁移其余桥接须保持技能编号顺序）；第 4 点剩余的存档牌种编码表往返，以及 `enc_winner` 用 `as u8` 写势力、解码走显式表的不对称，已随主稿 P0 于 2026-10-07 处理（加固批；2026-10-11 更正）。

### A1 结算机器去技能化

- **目标**：`kernel.rs` 中的通用结算机器（杀、决斗、AOE、濒死、无懈窗口等）不再出现任何具体技能名或技能专属字段。
- **做法**：
  1. 为每类结算列出标准时机（例：杀 = 使用时 / 指定目标后 / 成为目标后 / 需要出闪时 / 闪抵消后 / 造成伤害时 / 结算完毕）。时机名称以上游 `trigger` 事件名为对照表，写入 [玩法规则基准](native-rules-baseline.md)。
  2. 结算机器在每个时机派发事件，技能经 `Catalog::candidates` 触发，自己的中间状态保存在技能自身的机器中。
  3. 跨时机需要携带的数据（如酒的 +1、铁骑判红）放入结算帧上的**类型化附加数据槽**：键为 `SkillDefId` + 本地槽号，值为有限类型集合；附加数据槽进入快照与哈希。
  4. 逐个迁出 S1 中的字段：酒 → 铁骑 → 流离 → 护驾，每迁一个跑全量测试。
- **验收**：`rg -n "tieji|liuli|hujia|jiu_bonus" crates/engine-native/src/kernel.rs crates/engine-native/src/snap.rs` 在 `Sha` 相关结构中为零；全部既有测试通过；恢复矩阵与字节存档往返不退化；`ruleset_version` 递增并登记。

### A2 牌型开放

- **目标**：扩展牌不进入内核枚举。
- **做法**：`CardKind` 收缩为规则大类（基本 / 普通锦囊 / 延时锦囊 / 装备{武器, 防具, +1 马, -1 马, 宝物}）加少量规则必需的基础子类（杀的属性、闪、桃、酒、无懈）；具体效果由 `CardDef` 上的行为 ID 指向目录中的行为定义。`kernel.rs` 中按具体牌名的 `match` 改为按大类派发 + 行为回调。
- **验收**：`CardKind` 中不再含任何扩展包专属变体；新增一张扩展锦囊不需要修改 `catalog.rs`、`kernel.rs`、`snap.rs`、`archive.rs` 任一文件（用一张测试牌实证）；存档中牌种编码变化须递增格式版本。

### A3 宿主原语化

- **目标候选**：让扩展能组合稳定宿主能力，而不是每个效果都要求新增内核变体（S3）。
- **试验**：选两个行为差异较大的真实扩展效果，用已有原语和最小新增选择/状态接口表达；比较行为、恢复、调用成本和错误边界。描述式解释器只是候选，不预先要求重写全部 `HostBehavior`。
- **验收**：样本无需修改内核枚举即可安装并通过规则/恢复对照；只有该路线确实降低重复实现时再扩面。

### A4 原语补全

- **目标**：按实际来源需求减少 S4 中由原语缺失导致的差异。
- **做法**：
  1. 从所选纵向样本和[扩展台账](../migration/upstream-extension-reconstruction.md)先提取需要的原语：例如选牌区域/可见性、失去体力、展示、临时技能、翻面、事件取消与改判；其余按来源逐步补。
  2. 每个原语：类型化选择点接入统一选择通道（服从合法性与授权校验）、进入快照/哈希/字节编码、有保存恢复测试。
  3. 按原语逐条清理"登记差异"注释：能用新原语还原上游语义的，改实现并删注释；确属规则取舍的，移入 [玩法规则基准](native-rules-baseline.md) 并注明理由。
- **验收**：本轮选定来源的原语有正反例和恢复测试；对应差异能对齐或在规则基准中明确记为产品变体。注释计数只供检索，不代替行为验收。

### A5 快照、哈希、存档编码自动生成

- **近期最小修复**：枭姬/拆牌 tag 冲突及 A0 检查已完成；存档未知牌种与载荷读尽已于 2026-10-07 加固（异常输入拒绝+合法往返，不依赖生成器；2026-10-11 更正）。
- **条件方案**：若新增机器仍反复出现字段或 tag 漂移，再比较统一状态声明与现有手工编码加检查的维护成本。候选实现包括：
  - 工作区内过程宏 crate（需 `syn`/`quote` 构建期依赖，运行期仍只依赖 `blake3`）；
  - 或 `macro_rules!` 声明宏 / `build.rs` 从结构描述生成代码（零新增依赖）。
- **验收**：选中方案后字段、编码、哈希、恢复保持同源并有故障注入回归；格式变化明确版本门禁。无实测维护收益时不新增过程宏或构建生成器。
- **近期修复落地（2026-09-24）**：枭姬/拆牌 tag 冲突已修（XiaoJi=43，格式版本保持 v2，兼容取舍见[规则基准](native-rules-baseline.md)），A0 tag 唯一性检查与枭姬挂起字节往返/错 tag/短输入负例随 `cargo test` 运行；生成器条件方案未触发（本轮仅一处漂移，未构成「反复出现」）。

### A6 信息隔离类型化

- **目标**：策略与客户端边界只暴露合法座位信息；权威规则模拟可以在受控内部保留完整状态，但不能把真实暗牌泄漏给策略。
- **做法**：从一个现有询问/规划路径验证输入类型和数据流，复用未知池重分配；再推广到其他入口。
- **验收**：同信息集互换暗牌后，该入口的公开询问、座位视图和策略结果不变；逐入口扩面，不以简单禁止内部引用 `Engine` 代替信息流检查。

## 4 工作流 B：内容管线

### B1 内容来源与代码生成候选

- **待验证问题**：手写内置内容、旧 `.skill` DSL 与上游真实行为之间可能重复维护或存在语义缺口；现有旧线 catalog 的数量不等于保真率。
- **试验**：选一个有选择/恢复分支的技能，比较手写 Rust、现有 IR 生成和其他最小表示；先证明 IR 能无近似地表达其规则，再决定是否设为内置内容来源。旧 DSL 不是预先指定的唯一来源。
- **验收**：同上游输入和选择序列下状态/事件一致，生成物可复现；不支持的构造必须显式失败。是否批量生成以样本成本与覆盖证据决策。

### B2 双实现差分候选

- 当同一规则确有两个可执行实现时，固定牌序、随机源和选择序列，对照规范化状态、事件和选择点；差分只证明两个实现一致，**不能单独证明与上游规则等价**。
- 先做少量真实场景；只有失败定位和维护成本可接受，再接持续测试与模糊测试。

### B3 上游行为对照

- 先固定上游版本和少量行为样本，以相同牌序、合法输入和随机选择比较结果；人工/程序探针都可用。无头 Node 运行上游是候选，需先验证 DOM/平台依赖能被可靠隔离。
- 样本稳定后再考虑自动扩面和夜间 CI；差异须修复或写入[规则基准](native-rules-baseline.md)，不能因为旧线与新线一致就跳过上游核对。

## 5 工作流 C：扩展

### C0 生产侧装载器与名称所有权

- **目标**：复用已有生产实现（S11），完成其余测试桥接与实际宿主接线；同包重载复用名称，并明确新增唯一名称的拥有期/数量边界（S12）。
- **做法**：
  1. 复用已选定的 `content-native-loader`（ADR 0777/0778），保持 `engine-native` 运行期只依赖 `blake3`；不再讨论会反向形成依赖环的 `content-runtime` 择址。
  2. 装载器负责：读取已安装包、校验 schema 与宿主 API 版本、映射牌种和宿主行为、报告未映射项、产出 `ExtensionPack`。
  3. 按主稿完成剩余牌/角色/牌堆/初始化适配，保留 G1 原有断言；实际产品调用由原生宿主接线任务验收。
  4. 已有全局符号表复用不等于卸载回收；先明确唯一定义数量/驻留策略及包命名空间需求，需要回收时再比较目录拥有字符串等方案。名称进入摘要或存档时须保持字节一致或递增版本。
- **验收**：G1 原有行为与恢复断言保留；循环内重载同一包，名称/名单计数和指针稳定；新增唯一名称的边界另验，不把同包测试外推为总内存可回收。坏包、未知行为键和版本不符给出明确错误。
- **落地状态（2026-09-24，E02/G1 切片）**：择址新 crate `content-native-loader`（[ADR 0777](../adr/0777-native-c0-native-loader.md)——content-runtime 反向依赖会成环、engine-native 不引入 serde）；第 2 点装载/校验/映射/未映射报告已实现；第 4 点名称所有权经 `content::names` 符号表 intern 落地（类型保持 `&'static str`，名称入哈希/存档字节不变故版本不递增；循环内存验收用 `interned_count` 增量为 0 实证）；第 3 点迁移 gujian、wudian 两份 bridge（g1 测试名/数量/结果不变），其余 6 份为剩余切片；第 1/4 点的"坏包、未知行为键、版本不符"错误面已有验收测试。
- **审查更正与数据化（2026-09-24 晚）**：上条"循环内存验收"的循环只在循环外装载一次，且武将技能名单仍经 `Box::leak`（计数看不到），不足以证明重复装载有界。[ADR 0778](../adr/0778-native-c0-pack-data-keys.md) 之后：包元数据、射程、装备技写入 cards.json，牌种键、宿主行为键与牌种伴随技能由引擎全局表解析，装载器不再接收逐包参数（`PackSpec` 删除）；缺省势力/性别、越界点数/体力、重名或未登记技能均报错；武将技能名单走 `names::intern_list`；验收改为循环内每轮重新装载并断言名称/名单指针复用（先报红实证见[审查修复证据](../operations/evidence/2026-09-24-review-fixes/README.md)）。其余 6 份 bridge 已于 2026-10-07 全部迁移（炉石同批改用规范牌种键；2026-10-11 更正）。

### C1 扩展执行后端选择

- **必须满足的能力**：独立包经宿主接口执行新规则，选择可挂起/恢复，随机与资源调用受控，状态进入内容锁和存档；超额或故障不留下半次效果。
- **后端候选**：现有有界宿主原语、WASM 组件或其他受限运行时。WIT/wasmtime 可作为对照原型，不是已定方案；须用同一个真实扩展分别核对桌面、移动和浏览器可行性、调用成本与隔离边界，再写 ADR。
- **验收**：无需重编译客户端即可安装含新技能/牌的包，正常与恶意输入、跨进程恢复和失败回滚均有实测。
- **定案（2026-10-12）**：[ADR 0782](../adr/0782-extension-backend-and-legacy-js-scope.md)——内置内容用编译期 HostBehavior，扩展包规则用 rule-vm；WASM 暂缓；对照草稿的未证明项转为进度主稿 T8 的集成验收条件。

### C2 旧 JS 扩展兼容

- **已定范围**：两仓 37 个来源全部按功能重构支持；旧 JS 不承诺零改动运行（2026-10-12 用户决定 D2，[ADR 0782](../adr/0782-extension-backend-and-legacy-js-scope.md)）。`legacy-analyzer` 可辅助清点，不能把自动转换成功等同于功能验收。
- **候选（不立项）**：仅当出现 37 来源之外的具体零改动兼容需求、且可证明确定性、权限和恢复边界时，再评估 QuickJS 等兼容层；不得预设它能兜底任意 DOM/宿主补丁。
- **验收**：逐来源标注新接口重构、可选兼容层、功能缺口和实测证据；整包通过数只按[扩展台账](../migration/upstream-extension-reconstruction.md)更新。

### C3 包管理

- **做法**：包清单（ID、版本、依赖、冲突、所需宿主 ABI、内容锁摘要、签名）；安装、启停、更新、卸载与冲突检测；对局开始时锁定扩展集合并写入快照。复用 `content-runtime` 现有发现、导入与签名实现。
- **验收**：依赖与冲突解析、坏包回滚有测试；旧局所需版本可保留或重新取得，确实缺包/错版时给出明确拒绝原因。

## 6 工作流 D：AI

### D1 信息集蒙特卡洛树搜索（ISMCTS）

- **候选条件**：先把现有规划器的合法信息、决策质量、节点成本和取消行为测清；若一层规划明显不足，再比较 ISMCTS 与更小的搜索改进。
- **验收**：固定对局集、种子和计算预算下的质量提升与延迟有据，信息隔离和过期结果丢弃回归通过。未经测量不替换现有规划器。

### D2 快速模拟路径

- **条件方案**：只有剖析表明模拟中的回放/哈希是显著热点，才评估延迟记录或复用结果；**必须与正式提交共用同一套合法性校验与执行核心**，逐命令对照结果、状态、事件与随机流。
- **验收**：对照测试覆盖全部命令类型；在同负载基准下给出吞吐实测数据，写入 [原生基准](../operations/phase19-native-baseline.md)。

### D3 自我对弈强化学习

- **暂不立项**：目前没有固定质量基准、训练收益或产品需求证明需要强化学习；待规则与扩展覆盖、模拟器正确性和 AI 基准稳定后再评估。

## 7 工作流 K：客户端与联机

### K1 GPU 牌桌

- **候选做法**：先用一组真实牌桌场景比较 wgpu 与目标平台可用后端，表现层只消费合法视图/事件；是否共用桌面与浏览器渲染路径、是否拆线程由帧时间和输入延迟决定（见[性能架构 §8](../../noname-performance-architecture.md)）。
- **验收**：8 人局满手牌加动画在目标设备档位上满足性能架构中的帧时间标准。

### K2 动态皮肤

- **候选做法**：动态皮肤能力按两仓扩展清单保留；以实际素材验证格式、许可证、平台兼容和资源释放后再选运行时，不预定某个库。
- **验收**：动皮包抽样可正确播放；同屏 8 个动皮时帧时间满足标准。

### K3 联机

- **做法**：服务端权威执行；客户端只接收观察者视图增量；断线重连用"快照 + 事件日志"恢复。先复用可验证的现有传输，只有实测瓶颈或平台需求出现时再比较 QUIC / WebTransport。
- **验收**：断线重连后客户端视图与服务端投影哈希一致；抓包中不出现他人暗牌信息。

## 8 工作流 F：工程与流程

- **F1 旧线退役候选**：待原生线通过规则、扩展和产品验收后，再制定客户端、服务端、基准的切换及旧线退役 ADR；现阶段不把"冻结旧线"当作已决定事项。
- **F2 旧线拆 crate 候选**：只在旧线仍需长期维护且独立构建基准证明拆分有收益时立项；若将退役，不先做整仓结构迁移。
- **F3 构建与测试提速候选**：按[进度主稿 O2](native-progress.md#性能优化核验后的待办2026-09-24)先测干净/热构建；cargo-nextest、sccache 和测试文件合并分别试点。并行代理共用的 `target/` 不执行定期 `cargo clean`。
- **F4 模糊/变异测试候选**：优先覆盖已发现的存档 tag、目录构成、牌归属、选择恢复缺口；持续 fuzz 或 cargo-mutants 仅在产出可定位缺陷且运行成本可接受时扩大。
- **F5 CI 原生门禁**：先让当前全量原生测试恢复通过，再接稳定的定向/全量任务；A0 这类快速检查可随全量测试进入 CI，release runner、跨进程恢复及上游对照按耗时与可重复性分层加入。
- **F6 状态与 ADR 校验**：README/架构索引已只链接主稿；先为 27 个重复 ADR 编号建立小型查重检查，阻止新增冲突。测试/覆盖数字自动生成仅在人工同步反复出错且可定义可靠口径时立项。

## 10 如何使用本提案

实际任务从[进度主稿](native-progress.md)和[扩展台账](../migration/upstream-extension-reconstruction.md)选择；本页编号用于讨论替代方案和在任务中引用设计思路，不自动进入待办（挂靠关系见 §2）。每次只实现一个可独立验收的行为切片，必要时可跨内核、包和测试文件修同一根因。

立项一个"暂无主稿任务"的候选时，先在主稿或台账登记：独立需求、最小原型、替代方案、验收数据与负责人。实施结果、测试数与失败项写入主稿/台账和[证据目录](../operations/evidence/)；本页只在候选被采纳、否决或被证伪时更新结论和复核记录，不复制当前状态。

遵循工作区 [AGENTS.md](../../../AGENTS.md) 的源码核验、规则版本、证据和文档维护要求。修改规则或存档时用对应定向测试加原生全量回归验证；涉及旧线、跨端和性能时按实际影响补测。若本页假设与源码或用户范围冲突，更新提案与主稿后继续按已授权目标处理，不把未经验证的候选当作阻断条件。
