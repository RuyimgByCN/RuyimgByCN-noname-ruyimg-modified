# 行数门禁唯一的红：`effect.rs` 量化分析与拆分计划（2026-10-19）

> **结论先说**：拆分**在技术上可行**（拆分后预计 16 个文件、最大 1216 行），
> 但**本会话无法执行** —— 它需要改动 **1,217 个引用文件中的 1,069 个未跟踪文件**（他人工作区）。
> 因此门禁继续保持红，**原因已量化**，不再是「既有欠账」四个字。

## 1 现状（实测，不复述）

| 指标 | 值 |
|---|---|
| `crates/rule-api/src/effect.rs` 总行数 | **10 778** |
| 其中 `pub enum EffectRequest` 枚举体 | **10 573** 行（**98.1%**）|

⇒ **这不是「文件太长」，而是「一个枚举装了 815 个不同类型的请求」**。

### 关键发现

**除 `resolve` 外，其余 14 个桶全部天然合规**（最大的 `cards` 只有 1 216 行）。
**唯一的问题是 `resolve`**：**397 个 `ResolveXxx` 变体、5 513 行** ——
**至少需要再切成 3 份**（5513 / 2000 = 2.76）。

⇒ **拆分计划是「14 个领域模块 + `resolve` 按归属再切 3–4 份」⇒ 共 16–17 个文件，全部 ≤ 2 000 行** ✅

## 3 为什么本会话不做

| 障碍 | 数量 | 说明 |
|---|---:|---|
| 引用 `EffectRequest` 的文件 | **1 217** | 拆分枚举会改变所有构造点与匹配点的类型 |
| **其中未跟踪** | **1 069** | **87.7%** ——属他人工作区，**不可修改** |
| 已跟踪 | 148 | 仅这些可改，**不足以让工程通过编译** |

⇒ **即使只拆第一刀，也会立刻让 1 069 个未跟踪文件编译失败** ❌
⇒ **本会话能做的是「计划 + 度量 + 校验脚本」，不是「动刀」** ✅

## 4 `resolve` 桶的切分需要什么

**397 个 `ResolveXxx` 是按技能逐条实现的**（`ResolveYeyan`、`ResolveQixing`、`ResolveDrltPoxi`…）。
切分依据应当是**来源包归属**（`shahai` / `swd` / `gujian` / `yunchou` / `hearth` / `boss` …），
这与 `crates/rule-api/src/effect/` 下既有的 `resolve_dcyingtu.rs`、`resolve_houfeng.rs`
等**逐技能文件**是同一思路。

⇒ **但这需要代码生成器（`content-compiler`）的归属信息**，属**设计决策**：
**按下划线前缀猜包名会猜错**（本会话已因「猜名字」误判多次）。
⇒ **因此脚本只报告超限，不代为分组** ✅

## 5 复现

```bash
python3 -B scripts/plan_effect_request_split.py            # 报告
python3 -B scripts/plan_effect_request_split.py --check    # 有超限桶时 exit=1
python3 -B -m unittest scripts.test_plan_effect_request_split -v   # 11 个用例
```

**`--check` 当前 exit=1**：因为 `resolve` 尚未切分 —— 这是**预期信号**，
它把「门禁红」翻译成「`resolve` 还差 3 513 行」，可被 CI 或人工追踪进度。

## 6 对验收的影响

**行数门禁属工程规范，不属于 NC01–NC12 的功能验收门槛**：
- 它**不阻塞**功能实现与来源验收；
- 但它是**唯一长期红项**，会掩盖「新增文件是否超限」的信号 ——
  **因为门禁是「有任何文件超限即失败」，`effect.rs` 常年红着，新超限文件就被淹没了** ⚠️

⇒ **建议**：在无法拆分前，把门禁改为**「基线快照 + 只报新增超限」**，
否则这条守卫会持续失效。**该改动需维护者决定**（`scripts/` 属本会话可改，但语义变更应经确认）。
