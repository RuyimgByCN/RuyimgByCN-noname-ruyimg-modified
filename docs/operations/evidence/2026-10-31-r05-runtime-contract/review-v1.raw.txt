**Finding：P1，兼容承诺与当前严格版本门冲突（P:11、59、92）。**

`engine-native/src/engine/snapshot.rs:60` 要求 snapshot 规则版本等于重建 Catalog 版本；`K/archive.rs:180` 只接受当前格式。包锁不能让新 native 同时恢复旧规则330，保留旧 alias 也不能保留旧 dispatcher 行为。
最小修订：明确本批候选采用“新 reader 对不匹配规则／格式受控拒绝，保留原档和锁、不覆盖数据；旧外部 reader／制品仅按既有保留与安全退出政策留证”。若要迁移或继续产品运行旧局，另列准确输入版本、转换与退出条件待批，不能默认承诺并行旧 native，更不要求复活 engine-core。
`phase_begin→Judge` 可作为明确的过渡兼容入口，但不能据此宣称旧规则恢复，也不能把37来源中错误 alias 永久登记为差异；后续仍须迁移到对应真实时机。

**Finding：P1，Draw 异步迁移范围与接口尚未闭合（P:16、22–27、影响表②）。**

已限定检索 native kernel/content/engine 三处 src 的全部 `.draw_cards(...)` 实际调用。所见调用均丢弃返回的 `Vec<CardId>`，未发现直接使用返回值的调用方；但大量调用方依赖“调用结束时牌已入手／牌库已改变”，因此改返回类型不是主要问题。
具体反例：`C/content/host/step/xianjian_card_use.rs:110` 摸2后立即克隆手牌开选择；`step/mtg.rs:617` 摸2后立即生成弃牌选项；`step/yunchou.rs:293` 摸2后立即弃牌；`K/kernel/phase/draw.rs:165` 摸1后立即取手牌置顶；`K/kernel/tricks.rs:18` 摸牌后立即弃置锦囊本体。多目标循环及相邻两次 draw 也依赖顺序。
因此不能只迁主阶段补摸 caller，或同步发牌后补一个 phantom Draw parent。所有可能在 D 祖先下执行的普通 draw——standard/Host、VM DrawCards、J2 compound、伤害／濒死／死亡／卡牌机器——都需要真实 Draw→gain→子结算完成的边界；仅凭 `turn.phase==Draw` 无法筛选。
最小补件是一张限定 caller 分类表：哪些只需发 Draw 后返回、哪些拆出“摸后选／弃／移牌／下一目标”续行，哪些确证不可能位于 D 下；同时写明新异步入口的返回承诺，以及旧同步 API 的合法使用范围。不得保留其同步签名却改成排队语义。
`K/machine.rs:369` 当前先移牌后发 CardsDrawn，`K/kernel.rs:37` 明确该事件不是 gain 提交。P 必须指定抽出而未获牌的唯一持有者、过滤／防获得／取消时去向、等待中的 cards/step 保存位置，以及洗牌 RNG、Fault/abort 的回滚边界。`K/snap/ownership.rs:25` 当前不把 Frame.cards 当实体持牌；仅写 player/request 的新 Draw 载荷不足以证明中途归档合法。

**Finding：P1，来源先死后的避祸资格写错（P:41，验收8）。**

[上游 player.damage():8990](/Users/ruyimg/Documents/Claude/sanguosha/archive/upstream/noname/apps/core/noname/library/element/player.js:8990) 安装的 `filterStop` 会执行 `if (this.source && this.source.isDead()) delete this.source`；`gameEvent.ts:494` 每次 trigger 会调用它。因此“source 死了引用仍保留，可供存活 victim 的 End filter”与实际源相反。
最小修订：在 Source/End 各窗前遵守这项来源清理；若 Source 窗子结算使 source 死亡，后续 End 的 `dcbihuo.filter` 也可能因 source 已被删除而不成立。不能只检查当前技能 owner，也不能用不可变“原始来源”恢复资格。
同一 filterStop 在 num≤0 时触发 damageZero、finish 并置 `_triggered=null`，支持通常零伤害不进两后窗；`notrigger` 另有构造及 content 门控。成功 receipt 与窗口资格必须分开定义，不能由 `Some(n)` 单独授权两窗。
native `damage.rs:250` 后还有伤害修正；“最终事件 num”与护甲吸收量目前混在局部 amount 流程中。需列出认证写点、取消／转失血／零／吸收分支的决策表，不能仅称“统一认证”而不说明哪些共享伤害路径必须整理。

**Finding：P1，helper/mark 定义与依赖解析被当成现有能力（P:31–32、55–57）。**

`content-schema/src/package.rs:709` 的完整 ContentPackage 没有 mark 声明表；`:265` 的 PackageSkillEntry 也没有 helper role／expiry／onremove 元数据。PackageStore 的包依赖与逻辑哈希校验存在，但不会解析一个未定义的“mark 定义”。P 中“锁必须含匹配 helper/mark 定义”目前没有落点。

最小修订：选定并写明一个封闭方案——由 loader/Catalog 内固定 R05 角色表识别已验证的声明与同包 helper，或提出具体 schema 角色字段及其引用验证。必须给出 declaring package、逻辑 skill、helper role、稳定 mark key 的映射、冲突拒绝和哈希覆盖；“优先无字段”还不能提交审批。
第三方调用三个 compound 可复用 `K/rvm_bridge.rs:969` 的 J2 owner/skill 自绑定，但这不验证包归属、helper 角色、准确窗口或 mark 所有权。公开调用身份与固定同名 helper 之间怎样匹配，仍需准确写定。

**Finding：P1，零存在及 onremove 的完整边界尚未受保护（P:30–38）。**

`K/rvm_ops.rs:342` AddMark 相加为零即删除，`:357` RemoveMark 的 amount0／结果≤0会删除；`:91` 接收层只验 player，没有 reserved-mark 授权。任意现有 AddMark/RemoveMark 若碰到新全局裸 ID，就能破坏 next/current 的零存在和 helper 一致性。
最小修订：四槽由经验证的 R05 内容操作独占写入；旧通用效果及带 mark 参数的 compound 对这些保留槽采用明确拒绝／受限授权。数值为零时 helper 可存在；死亡 next 保留、禁用保值、显式移除删值须分别验证，不能用 `MarkCount==0` 判断缺失。
当前 `RemoveSkill` 在 `rvm_ops.rs:417` 按 def 跨 owner retain，临时到期在 `machine.rs:725` 仅禁用，死亡／替补在 `kernel/death.rs:98,147` 直接 remove。不能把这些直接当 owner-scoped onremove。补一张四 helper 的删除入口表及限定回调接入范围即可，无需通用生命周期框架；reserveDead/excludeMark 所依赖的真实模式信息也须标明来源，未有实现的分支不得写成已支持。

**Finding：P1，窗口授权与流程机器绑定还缺可审核的类型关系（P:16、49–52、验收11）。**
