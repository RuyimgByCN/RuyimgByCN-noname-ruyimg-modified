**Finding：P1，验证上下文与实际 Engine packs 之间仍可分离（P:25、42）。**

P:25 保护了 `VerifiedLockedContent` 的构造，也要求 bridge 只读取验证结果；但 P:42 的拟议 API 仍同时接受 `snapshot, packs, verified_content`，并只明确检查 **packs provenance==verified 集合**。这验证的是来源标签，未保证传入 packs 的规则字段仍是验证结果的派生产物。

现有 `ExtensionPack.cards/host_skills/vm_skills` 均为可修改的公开字段（`crates/engine-native-content/src/content/extension.rs:104`）；`CardDef.range/rank` 同样公开（`crates/engine-native-kernel/src/catalog.rs:578`）。`standard_catalog_with_extensions` 直接复制这些规则字段构目录（`content/standard.rs:481`），当前恢复门则比较 Catalog 版本并校验状态/引用（`engine-native/src/engine/snapshot.rs:45,60`）。

具体反例：从合法验证上下文桥接 packs 后，修改一张装备的合法 range，保留其 provenance、包身份及验证上下文，再调用拟议恢复 API。按 P:42 已写明的条件，身份集合仍相等，牌数量和所有权引用也可全部合法，但恢复后的攻击范围已不对应被锁定的原始资产。改进原字节保存不能单独消除这个分离点。

**最小修订是收紧一个接口，而非再算一份哈希：**

- 新 locked 路径只接受验证上下文，由受控接缝从其中的已验证包/资产构建 Catalog；不再另收可替换的裸 `ExtensionPack` 集合。
- 或明确规定 bridge 返回不可伪造、不可独立修改规则内容的派生包句柄，Engine 只接受该句柄；provenance 检查是辅助检查，不能单独成为内容绑定证明。
- 新局、恢复和 WAL 使用同一种绑定保证；普通手建 packs 入口不能携一个来源标签就进入 locked 路径。

若 v4 原意已经是后一种封闭句柄，只需把该约束写进 P:25/42，消除当前三参 API 对裸 packs 的歧义。无需新增 core 字段、R05 指纹、锁算法或权限框架，也不必为了这一点扩大其余审查范围。
