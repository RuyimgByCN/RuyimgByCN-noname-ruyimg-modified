**Finding：P1，原局完整 ContentLock 的输入与原始字节来源尚未闭合（P:29–31）。**

v3 要求所有恢复入口传入“原局既有 ContentLock 及锁定包/冻结字节上下文”，但当前各端的同名数据不是同一类型，也不是相同哈希输入：

| 实际接缝 | 当前源码事实 |
|---|---|
| 浏览器保存/恢复 | `apps/web-client/src/engine/extensionStore.ts:413` 的 `NativeSaveSlot.contentLock` 是 `string[]`；`nativeMatchContent.ts:19,60` 保存/重算的是包键列表、logic-hash lockSeed 和重新序列化的 packsJson，不是 Rust 完整 ContentLock。 |
| WASM → native | `crates/engine-native-wasm/src/session.rs:30` 的 `engine_from_archive(hex,packs_json)` 没有原局锁参数；安装载荷在 `installed_packs.rs:27` 解析为对象并桥接，使用的是该对象序列化后的 digest。 |
| 服务端保存/恢复 | `apps/game-server/src/room_native.rs:34,391` 保存 pack_refs、冻结包并接收 packs；没有直接保存/传入聚合 ContentLock。冻结包已有可复用的 `LockedPackage + package_json + assets`（`native/frozen.rs:11`）。 |
| 核心恢复及 WAL | `E/engine/snapshot.rs:45,60` 接收 snapshot/packs 并比较 Catalog 规则身份；`apps/game-server/src/room_native/wal.rs:160` 也只把 packs 交给恢复，不能遗漏这个重建路径。 |

更关键的是 `LockedPackage.content_hash` 按**原始 package bytes**计算：`content-runtime/src/sign.rs:20`、`store.rs:224,281`；服务端冻结验证也按 `package_json.as_bytes()` 核对（`native/frozen.rs:38`）。
因此，把现有浏览器 packsJson 解析再序列化，不能一般性地恢复该哈希输入。一个只改变 JSON 空白、逻辑对象不变的包就有相同 logic hash、不同 content hash；当前浏览器保存格式没有保证保留最初安装的那些字节。更不能拿当前安装副本或重算出的新锁冒充原局锁。

**最小修订只需补一张恢复接缝表，不需要新增 core 字段或 R05 锁：**

1. 定义新局保存时原局完整锁和精确包字节从何处取得、落在现有信封的哪个字段；浏览器现有字符串列表/lockSeed 如何与它区分。
2. 写明 WASM、server from_saved/WAL、native restore 的拟议参数如何携带该上下文，以及同一匹配过程在哪里完成；标准空包局与缺上下文的旧扩展档分别走什么候选政策。
3. 明确 content_hash 的字节口径：保留并验证原安装字节，或另提所有端一致的规范化契约。不能在某端默默换成对象重新序列化的哈希。

这是对已选择“唯一锁链”的具体补齐，不要求并行旧 dispatcher、第二身份系统或全面包框架。缺失上下文时受控拒绝仍可作为待裁决候选，但必须与新保存格式能实际提供的上下文相配。
