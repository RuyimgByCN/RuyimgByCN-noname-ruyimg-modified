## 2. 首次失败、复核加固与修复记录（按 AGENTS.md 分开登记）

1. **`up37_r02_to_n07_complete_closure` 首跑捕获的 5 处问题与修复**：
   - ① `up37_r04` 与 `up37_n02` 中 VM 触发技通过 `HOST_EFFECT_EXT STORAGE_SET`（`tag = 649`）派发时，因 `def_id >= 0x8000_0000` 转 `i32` 为负数被 `rule-vm` 的 `value.max(0) as u32` 钳制为 `0`：在 [`crates/engine-native-kernel/src/rvm_ops/commit_up37.rs`](../../../../crates/engine-native-kernel/src/rvm_ops/commit_up37.rs) `try_commit_up37_storage_set` 补齐按 `executing` 技能名的回退分派，使 VM 字节码触发与直接 `EffectRequest::StorageSet` 双路径一致生效。
   - ② `resolve_dcsbzaoji` 在无活跃事件帧（`ctx.res.stack.is_empty()`）时直接调用 `ctx.current_damage()` 触发栈非空断言：增加 `!ctx.res.stack.is_empty()` 守卫后解决。
   - ③ `resolve_potcuifeng` 初版误读 `player(owner).turn_damage`（内核中该字段记录本回合造成的伤害而非受到的伤害）：改为读取 `turn_var(ctx.core, owner, "damaged_this_turn")` 后解决。
   - ④ `up37_r03`／`up37_r06` 测试初版使用非标准卡名 `"lebusishu"`／`"zhugeliannu"`（标准目录键为 `"le"`／`"zhuge"`），以及 `up37_r07` 对 `commit_phase` 立即弹出 `extra_phases` 的阶段步数假设偏差：对齐为 `"le"`／`"zhuge"` 与真实阶段推进序后通过。
   - ⑤ `up37_i02` 初版连续执行两次 `debug_commit_effect(KillPlayer)` 后仅在末尾调用一次 `release_committed_presentation()`（第二段覆盖了第一段的 `Sealed` 区间）：改为每次命令后分别释放并提取 `PublicPresentationBatch` 后通过。
