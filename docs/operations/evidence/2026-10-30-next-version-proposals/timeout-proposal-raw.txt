## 建议的一条最小完整实现路径（未实施）

### 1. 内部动作：记录选择结果，不让恢复再次调用 AI

原生 GameAction **只新增**：

```rust
TimeoutAction {
    choice_id: u64,
    selection: Vec<ChoiceOption>,
}
```

actor/expected_revision/dedup_id 已在 GameCommand 中，不复制到 action；不加时间戳、AI种子、嵌套任意 GameAction 或由客户端声明的 system bool。TimeoutAction 只用于首次到时接管的这一条回答。后续托管回答仍显式提交 **Answer { choice_id, selection }**；非选择时的托管阶段推进仍是 **NextPhase**，每步都记录实际动作，不靠恢复重算策略。

在 submit 的挂起门及终局挂起应答例外中把 TimeoutAction 与 Answer 同等处理；apply_command 两变体并入**同一个**应答校验分支，actor 必须仍等于 open.observer，候选和取消复用 accepts。没有 pending、过期 choice、错观察者、非法/重复 selection、旧 revision、旧 dedup、故障/预算拒绝时都不产生托管效果。规则核不检查到期时间，也不维护 managed。

权限是宿主入口的能力边界：新增 `pub(crate)` session 超时提交函数，仅 native actor 的内部到期分支调用，调用参数由当前 choice 和持久化 deadline 得出；不得新增 RoomMsg/WS/Worker 任意原生命令提交入口。native `action_for(CommandKind::TimeoutAction {..})` 必须继续拒绝（可改为明确稳定拒因）；public/legal_actions、native_view 映射和 WASM action_to_json 绝不产生 TimeoutAction。WASM绑定保持现有 answer/next_phase 入口，内部Rust一致性测试可直接构造该动作，不导出可由页面调用的 timeout binding。拒绝报文自报系统actor/timeout字段；spectator及未来Referee同样无此特权。

### 2. AI与托管：简单的只读策略，分步交回 actor

复用 PolicyInput / Own ChoiceView，采用当前测试与 `examples/n10_table.rs:27` 已有“按候选顺序选最少合法项”的基线：从本人授权选项取前 min 个不同值，min=0时空选合法；生成 Answer 后仍走正式内核校验。不是照搬例子中 `.max(1)` 的快捷行为，也不在策略中调用 submit/run_policy（后者会先修改引擎且使用另一套dedup）。这个策略只看到本人投影，不访问真实暗手牌/牌库，不模拟未知挂起机器，不新增AI依赖或搜索配置。

首次 timeout 成功后 managed_seats 标记该内核座位，包括暂未有人入座的合法座位；后续该座位 Own Choice 立即排一个显式 Answer，轮到该座位且无选择时排一个 NextPhase，沿用同一提交/WAL事务。每次最多推进一条，然后让 actor 处理外部消息，不能在一个分支 while 自动跑整局。这里是最低能力的代答/推进基线，棋力、主动技搜索和通用AI池仍归 NC10，不能以本批冒充AI质量验收。

本人**新的合法操作被接受**或有效令牌重连成功时清托管，变化与该操作/重连一起耐久提交；快照/心跳、非法包、旧收据重放不清。此“本人操作”的精确定义在审批问题中写明，避免用拒绝报文或历史重放抢回调度权。断线不清 managed，重启保留；reclaim只换成员，不能改变座位当前托管/选择结算。旧连接在重绑定后无控制权。

### 3. 房间元数据与时钟：同一个 JSON/事务，不加 store

NativeRoomState 尾部增加两个**可省略 aggregate**：`timeout: Option<NativeTimeoutState>` 和 `wal: Option<NativeWalState>`，均 default None + skip_serializing_if None。新版本新房间必须有 Some；旧房间缺字段反序列化后仍按旧字段序列化，从而**不改变旧校验和**。from_saved 先做归档/规则门禁，再要求当前规则的新房间元数据完整，不能给旧规则档补默认值后升级。

```rust
struct NativeTimeoutState {
    choice_timeout_secs: u8, // 只能10/15/30/60/90；新房间默认30
    managed_seats: Vec<u8>, // 按座位排序，无重复，全部<max_seats
    deadline: Option<NativeChoiceDeadline>,
}
struct NativeChoiceDeadline {
    choice_id: u64,
    observer: u8,
    deadline_unix_ms: u64,
}
```

deadline必须与当前 OpenChoice 的 id/observer一致；无选择时为None。它不绑定revision：补偿RevealGeneral会推进revision却保留同一选择，不能因此重置倒计时。新选择提交时生成截止时间，与引擎、managed、收据及WAL同一候选落盘，只有持久化确认后发布；同选择的 Snapshot、断线、重连、重启、Recover 不加时。初建即挂起的房间在初次持久化时也要建立 deadline。

**建议批准的恢复政策**：截止值为服务端 SystemTime 的 Unix毫秒绝对时间，与现有Pong同一时间语义；停机时间计入时限，恢复时未来截止继续剩余时间、过期截止排一次当前选择的timeout。有效重连先清托管，但不延长仍挂起的选择时间；到期后仍可能再被接管。actor 可用 tokio timer 等待由同一服务端截止值计算的剩余间隔，唤醒必须重新核对 SystemTime 和 choice；不能把 std::Instant 落盘或把Pong当作单调时钟。进程内时钟回拨会增加等待，前拨会使选择提前到期，这是绝对时间政策的明确边界；生产校时/时钟错误应显式报错，不能把时钟失败当0并自动接管。用户可见倒计时是近似显示，客户端时钟永不决定规则提交。

### 4. 真实动作 WAL：补入现有 NativeRoomState serializer

将 NativeRoomPersist 的有效“基准快照+命令段”纳入 session/checkpoint 的可回滚数据并导出到上面的 `wal`，由现有 StoredRoom/serde_json/checksum/journal 一次保存；复用现有 snapshot_every 做段检查点，不新建数据库/文件/服务。记录所有实际推进的动作，人工与托管之间的中间命令不能缺失。

```rust
struct NativeWalState {
    base_snapshot_hex: String,
    entries: Vec<NativeWalEntry>,
}
struct NativeWalEntry {
    actor: u8,
    expected_revision: u64,
    dedup_id: u64,
    action: StoredNativeAction,
    revision: u64,
    state_hash: [u8; 32],
}
```

在 server 现有 room_native 子模块内放一个小的私有serde DTO codec：StoredNativeAction 与当前 GameAction 的6种变体一一对应（PlayCard/NextPhase/ActivateSkill/RevealGeneral/Answer/TimeoutAction），其 selection 使用同样6种值的 `StoredChoiceOption::{Confirm,Pass,Card(u32),Player(u8),Tag(u8),Kind(u16)}`，转换穷举匹配，不依赖Debug字符串或裸u32混用。内核新增变体使匹配编译失败即可提醒维护；不为几行JSON编码给两个核心crate增加serde或开放archive私有函数。当前 ChoiceOption::Kind 的解码门禁/数量界限等在服务器DTO恢复校验保留，未知类型、超界、过大选择及无效WAL链明确拒绝。

候选提交顺序：checkpoint →构造实际 GameCommand（用 session.next_dedup，checked递增）→ Engine::submit →成功后在候选中同时追加**这条实际命令**、设置/清managed、建立后继deadline、记玩家收据→ durability.commit →发布个性化状态/名册。**不能沿用当前“先commit再record”的时序。** 非revision推进的 StartGame兼容空操作不造伪WAL；成功 assign_general 不推进revision但改状态，沿用其替换快照恢复点的语义，重置WAL基准而非制造无法重放的缺口。

Recover/from_saved重放保留的命令段必须使用原 expected_revision/actor/dedup/selection，检查每条result revision/hash及最终完整规范快照（包括last_dedup/RNG/续行），与保存的snapshot_hex一致；去掉现有Recover的人造 `revision*2`。TimeoutAction重放纯粹走Answer逻辑，不检查时钟、不给AI第二次机会；managed/deadline从同一确认房间元数据恢复。段可随既有快照策略压缩，压缩后的检查点就是旧命令效果的恢复依据；这不是永久录像历史完整交付，原NC09录像待办仍保留。

### 5. 竞争、幂等和失败边界

单写actor一次只提交一个候选。建议定义：actor选取消息前先检查已经到期的当前deadline；到期与消息同时就绪时timeout优先；此前已取出并正在处理的人工命令先完成。这是actor观察到的顺序，绝不承诺按客户端点击时间或报文发送时间排序。不要使用可被源源不断消息饿死的“总是rx优先”select；自动后继每条回到调度边界。

- 人工先成功：choice消失/变更，旧timer按(id,observer)失效；不能给下一窗套旧timeout。timeout先成功：人工旧答被拒；无重复扣牌/事件/RNG。若只是RevealGeneral而保留同choice，保留截止，在提交timeout时取**当前**revision。
- 系统timeout不占玩家(token,key)命名空间：其幂等使用既有GameCommand dedup水位 + 已耐久的(choice,deadline)/WAL状态；不为系统伪造NativeCommandReceipt或令牌。重复唤醒在最新选择和已接受命令上核对后不再执行。人工重试继续走当前command_receipt，完全相同请求返回原结果、同键异载荷冲突、replay无收据拒绝。
- 内核拒绝/故障：不追加WAL、不消耗确认dedup、不标managed、不发布成功；保持原deadline。不可对必拒选择进行无让出的零延时循环；记录不含私牌/令牌的稳定故障并暂停该窗口自动重试，待明确新操作/恢复后再评估。
- 持久化前失败：整个候选（engine、dedup、deadline、managed、WAL、收据）回滚；没有成功ack/广播。retry不得因只回滚engine而留下managed或已消费timer。
- rename后不确定：原RoomDurability规则照用；replacement_visible要求先固定确认状态，decision_uncertain/补偿失败要求重启。不能让timer绕开checkpoint继续写。重启只按Prepared/Committed实际决定恢复：已提交则不再重答，未提交则只从旧确认状态重新产生一次候选；向客户端如实报不确定，绝不假报取消成功。

## WS字段与版本：不能在事实不足时承诺WS5

建议最小公开变化只在房间协议，不扩展内核ChoiceKind或Worker命令：

1. `ClientMessage::CreateRoom` 新增 `choice_timeout_secs: Option<u8>`；None=30，仅接受五个值，非原生房间明确拒绝非默认设置而非静默忽略。Lobby→spawn_native_room_if_configured→session设置→首次耐久保存完整接线；创建UI提供同五个选项。
2. `ServerMessage::RoomRoster` 新增 `choice_timeout_secs: Option<u8>`（旧线None，原生Some）；`SeatPresence` 新增 `managed: bool`（旧线false）。以现有创建/重连/状态更新的名册广播显示实际配置与托管，不能客户端自行猜。新增字段同步Rust和networkClient.RoomRoster/产品UI及旧线构造者。
3. 不改全局 engine_api::ChoiceRequest：在已有 `ServerMessage::{JoinOk,Snapshot,CommandOutcome}` **各新增** `choice_deadline_unix_ms: Option<u64>`，只在该观察者有personal choice时给值，和choice同报文防串窗。相应 `room::JoinReply`、Lobby组包、native actor三条输出、TS解析和OnlineSession/恢复路径同步；旧线None。客户端已有Pong服务端Unix时间可用于显示同步，不能新造控制命令或借continuation_id传时钟。
4. 条件式 **WS5→WS6** 随本字段集审批；若Referee先获批并落WS6，则本字段在同一待发布的WS6合约中合并，不再自行分配WS7。所有旧线/原生协议构造和序列化测试同步。旧WS5客户端明确VersionMismatch，缺新字段拒绝，不依赖serde忽略未知字段的偶然行为；WS6先Hello并验证版本才允许建房/入房/提交。当前Hello只返回错误，且header版本被Lobby重建，故仅改常量不构成拒旧门禁，必须加会话握手状态/公共入口校验；同步客户端Welcome校验，防反向连到WS5后端。现有0=unspecified不能绕过本WS6新房间合约。

这是本稿唯一推荐路径：需用户批准新wire fields/兼容门禁。只做全服固定30秒、用现有None策略字段或在UI硬编码可选值，均不满足已批准的房间配置与实际托管反馈。
